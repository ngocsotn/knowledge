# OAuth 2.0 & OpenID Connect (OIDC)

OAuth 2.0 is the industry-standard protocol for authorization, and OIDC is an identity layer built on top of OAuth 2.0 for authentication.

---

## 1. Meaning & Core Roles

OAuth 2.0 is designed to grant a third-party application limited access to a user's resources without exposing the user's credentials.

### The Four Roles
1. **Resource Owner:** The user who owns the data (e.g., the person with a Google account).
2. **Client:** The application requesting access (e.g., a SvelteKit blog wanting to sign in via Google).
3. **Authorization Server:** The server that authenticates the user and issues tokens (e.g., Google accounts server).
4. **Resource Server:** The API hosting the protected user data (e.g., Google Contacts API).

---

## 2. Standard OAuth 2.0 Grants/Flows

### A. Authorization Code Flow with PKCE (Proof Key for Code Exchange)
* **Standard for:** Single Page Applications (SPA), Mobile Apps, and Web Apps.
* **Why PKCE is mandatory:** In public clients (like SPAs), an attacker could intercept the authorization code from the URL redirect. PKCE prevents this by adding a temporary cryptographic challenge:

#### PKCE Sequence Diagram:
```
 Client (Browser)                  Auth Server (IdP)             Resource Server (API)
       │                                  │                                │
       ├─ 1. Generate verifier + challenge │                                │
       ├─ 2. Redirect with challenge ────>┤                                │
       │     (challenge = SHA256(verifier)) │                                │
       │                                  │                                │
       │  [User Authenticates & Approves]  │                                │
       │                                  │                                │
       <─ 3. Return Authorization Code ───┤                                │
       │                                  │                                │
       ├─ 4. Exchange Auth Code + verifier ─>┤                             │
       │                                  │ (Validates verifier vs.        │
       │                                  │  stored challenge)             │
       <─ 5. Return Access/ID Token ──────┤                                │
       │                                                                   │
       ├─ 6. Access Private API with Bearer Token ────────────────────────>┤
       <─ 7. Return Private Resources ─────────────────────────────────────┤
```

#### The PKCE Algorithm:
1. **Code Verifier**: A high-entropy, random cryptographic string generated by the client:
   $$\text{Verifier} = \text{random\_string}(43, 128 \text{ chars})$$
2. **Code Challenge**: The SHA-256 hash of the verifier, Base64Url-encoded:
   $$\text{Challenge} = \text{Base64Url}(\text{SHA-256}(\text{Verifier}))$$
3. **Verification**: During the token exchange, the Auth Server calculates the SHA-256 hash of the submitted `code_verifier` and matches it against the initial `code_challenge` sent in step 2. If they match, the server knows the client requesting the tokens is the exact same entity that initiated the login.

---

### B. Client Credentials Flow
* **Standard for:** Machine-to-Machine (M2M) communication (e.g., backend billing service talking to an inventory API).
* **Mechanism**: There is no user interface or resource owner interaction.
  1. The client backend sends its `client_id` and `client_secret` directly to the Auth Server.
  2. The Auth Server validates the credentials and returns a short-lived Access Token.
  3. The client backend uses this token to call protected resource servers.

---

### C. Implicit Grant (Deprecated)
* *Historical:* Returned access tokens directly in the URL redirect fragment.
* *Why Deprecated:* Tokens were leaked in browser history, proxy logs, and referrer headers. SPAs must now use **Authorization Code Flow with PKCE**.

---

## 3. OAuth 2.0 vs. OpenID Connect (OIDC)

* **OAuth 2.0 is about AUTHORIZATION (Delegated Access):**
  * *Token returned:* **Access Token**. Used by the client to request data from the Resource Server.
  * Answered question: *"Does this app have permission to read my emails?"*
* **OIDC is about AUTHENTICATION (Identity):**
  * *Token returned:* **ID Token** (always a formatted JWT) + Access Token.
  * Answered question: *"Who is the logged-in user?"*
  * Standardized endpoints: Introduces `/userinfo` to fetch verified profile details.

## 4. Popular Interview Questions & High-Impact Answers

### Q1: What is the purpose of PKCE in OAuth 2.0, and why is it recommended over the standard Authorization Code Flow?
* **Answer:** In traditional Authorization Code Flow, public clients (like React/Svelte apps or mobile apps) cannot protect their `client_secret` securely on the device. An attacker could intercept the authorization code from the browser redirect and exchange it for a token. **PKCE** removes the need for a static `client_secret` by using dynamic challenges: the client verifies its identity dynamically by proving it holds the unhashed secret (`code_verifier`) that matches the hashed challenge sent at the start.

### Q2: What is the difference between an ID Token and an Access Token?
* **Answer:** An **ID Token** is an OIDC-specific JWT designed for the **Client application**. It contains user profile attributes (email, name) and is read by the frontend to display identity. An **Access Token** is an opaque or JWT string designed for the **Resource Server (API)**. The frontend does not read it; it simply includes it in authorization headers so the backend API can authorize requests.

### Q3: What is the "state" parameter in OAuth redirects, and what attack does it prevent?
* **Answer:** The `state` parameter is a random string generated by the client before redirecting the user to the Auth Server. The Auth Server echoes this exact `state` back in the redirect callback. The client must verify that the returned state matches the initial value. This protects against **CSRF (Cross-Site Request Forgery) in OAuth**, preventing attackers from forcing a user to link their app profile to an attacker's social account.
