# OAuth 2.0, OpenID Connect (OIDC) & Enterprise Identity Federation

Comprehensive staff-level study guide covering delegated authorization (OAuth 2.0), identity federations (OIDC, SSO), offline access, multi-tenant JWT architectures, and advanced interview questions spanning all authentication topics.

---

## 1. OAuth 2.0 & OIDC Core Foundations

### Standard OAuth 2.0 Roles
1. **Resource Owner**: The end-user who owns the data and grants access to it.
2. **Client**: The application requesting access to resources (e.g., a SvelteKit SPA, mobile app, or backend cron job).
3. **Authorization Server**: The engine that authenticates the user, obtains consent, and issues tokens (e.g., Okta, Auth0, Keycloak).
4. **Resource Server**: The API hosting the protected user data (verified via access tokens).

### Standard OAuth 2.0 Grants/Flows

#### A. Authorization Code Flow with PKCE (Proof Key for Code Exchange)
Mandatory for public clients (SPAs, mobile apps) that cannot securely store a `client_secret`. It replaces static secrets with a dynamic cryptographic challenge.

```
 Client (SPA)                      Auth Server (IdP)             Resource Server (API)
      │                                  │                                │
      ├─ 1. Generate Verifier + Challenge │                                │
      ├─ 2. Redirect with Challenge ────>┤                                │
      │                                  │                                │
      │   [User Authenticates & Consents]│                                │
      │                                  │                                │
      <─ 3. Return Auth Code ────────────┤                                │
      │                                  │                                │
      ├─ 4. POST Auth Code + Verifier ──>┤                                │
      │                                  │ (Validates Verifier vs.        │
      │                                  │  stored Challenge)             │
      <─ 5. Return Access + ID Token ────┤                                │
      │                                                                   │
      ├─ 6. GET Resource (Bearer Access Token) ──────────────────────────>┤
      <─ 7. Return Protected Data ────────────────────────────────────────┤
```

* **The Cryptographic Engine (PKCE)**:
  - **Code Verifier**: A high-entropy random string generated by the client:
    $$\text{Verifier} = \text{random\_string}(43 - 128 \text{ chars})$$
  - **Code Challenge**: The SHA-256 hash of the verifier, Base64Url-encoded:
    $$\text{Challenge} = \text{Base64Url}(\text{SHA-256}(\text{Verifier}))$$
  - **Verification Gating**: During token exchange (Step 4), the Auth Server calculates $\text{SHA-256}(\text{submitted\_verifier})$ and matches it with the registered `code_challenge`. This guarantees that the client exchanging the authorization code is the exact same client that initiated the authentication request.

#### B. Client Credentials Grant
Used for **Machine-to-Machine (M2M)** integrations (e.g., background cron jobs, billing microservices).
- **Mechanism**: No user interface or end-user interaction.
- The client sends its `client_id` and `client_secret` directly to the Auth Server via a POST request.
- The Auth Server returns a highly restricted, short-lived Access Token.

## 2. OpenID Connect (OIDC) Identity Layer

OIDC is an identity layer built on top of OAuth 2.0. While OAuth 2.0 is purely about **delegated access** (permissions), OIDC introduces **identity verification** (federated authentication).

```
  Layer          Protocol               Core Token            Target Audience     Question Answered
  ─────────────  ─────────────────────  ────────────────────  ──────────────────  ───────────────────────────
  Authorization  OAuth 2.0              Access Token (Opaque) Resource API        "What permissions does client have?"
  Identity       OpenID Connect (OIDC)  ID Token (JWT)        Client Application  "Who is the authenticated user?"
```

### OIDC Mechanisms
* **The Scope `openid`**: The client must request the `openid` scope. This triggers the Auth Server to return an **ID Token** alongside the Access Token.
* **The ID Token**: A cryptographically signed JWT containing claims about the authenticated user (e.g., `sub` user ID, `email`, `name`, `auth_time`).
* **The `/userinfo` Endpoint**: A standardized, protected OIDC endpoint. The client can send the Access Token to this endpoint to retrieve verified user profile attributes.

## 3. Enterprise Identity: Offline Access, SSO, and Federation

### A. Offline Access (`offline_access`)
* **Mechanism**: To gain access to a resource when the user is offline (e.g., background mail syncing), the client requests the `offline_access` scope.
* **Result**: The Authorization Server returns a **Refresh Token** alongside the Access Token.
* **Security Guard**: Refresh tokens requested with `offline_access` must be strictly secured (HttpOnly cookies or encrypted vaults) and governed by Refresh Token Rotation (RTR).

### B. Single Sign-On (SSO)
SSO allows a user to authenticate once at a centralized **Identity Provider (IdP)** and gain access to multiple independent applications (Service Providers - SP).

```
 Application A (Client)               Central IdP                  Application B (Client)
        │                                  │                                  │
        ├─ 1. Redirect to Login ──────────>┤                                  │
        │                                  │ (User enters credentials)        │
        │                                  │ (Sets SSO Session Cookie)        │
        <─ 2. Return Tokens (Sign In) ─────┤                                  │
        │                                  │                                  │
        │                                  │ ─── Later User Navigates to B ───│
        │                                  ├─ 3. Redirect to Login ───────────┤
        │                                  │ (Sees active SSO Cookie, auto-log)│
        │                                  <─ 4. Return Tokens (Auto Sign In)─┤
```

* **SSO Session Cookie**: The centralized IdP sets an encrypted, HttpOnly session cookie on its domain (e.g., `idp.company.com`).
* **Silent Authentication**: When Application B redirects the user to the IdP, the browser automatically attaches the SSO session cookie. The IdP detects the active session, bypasses credential entry, and immediately issues tokens to Application B via redirect.

### C. Identity Federation (Federated Trust)
Identity Federation bridges user directories across distinct organizational boundaries.
* **Trust Protocol**: Built on secure trust relationships established using exchange certificates (SAML 2.0 or OIDC).
* **Enterprise Login (e.g., Active Directory / SAML)**: An employee logs into a SaaS tool using their internal company credentials. The SaaS tool (Service Provider) delegates authentication to the company’s internal Active Directory (Identity Provider) via SAML or OIDC redirects.
* **Social Login (e.g., Google, Facebook)**: A consumer signs into an e-commerce store with "Log in with Google". The e-commerce tool trusts Google’s signed OIDC tokens to verify the customer’s email and identity.

## 4. Multi-Tenant JWT Design & Architecture

In SaaS environments where multiple enterprise customers (tenants) share a single software deployment, the authentication architecture must enforce strict data isolation.

```
 Client (Tenant Acme) ──(Header: JWT iss=auth.com/acme)──► [API Gateway] ──(Injects X-Tenant-ID)──► [Downstream Services]
                                                               │                                      │
                                                               ├─► Fetch Public Key via               └─► Database Isolation
                                                               │   auth.com/acme/jwks.json                (Row-Level Security)
```

### A. Core Multi-Tenant JWT Design
1. **Tenant Claims**: Inject tenant identifier claims into the JWT payload during generation:
   - `tid` (Tenant ID): `acme_corp`
   - `iss` (Issuer): Tenant-specific issuer string (e.g., `https://auth.provider.com/acme_corp`).
2. **Tenant-Specific Signing Keys**:
   - For high isolation, sign each tenant's tokens using a tenant-specific private key.
   - Expose public keys at tenant-specific JWKS paths: `https://auth.provider.com/tenants/<tenant_id>/.well-known/jwks.json`.
3. **Gateway Routing and Verification**:
   - The Gateway inspects the token's `iss` claim or extracts a subdomain (e.g., `acme.saas.com`) to identify the tenant.
   - It fetches the tenant-specific public key from the matching JWKS endpoint and verifies the signature.
   - The Gateway injects `X-Tenant-ID` into downstream headers to drive database routing or PostgreSQL Row-Level Security (RLS).

## 5. Comprehensive Auth & Auth Interview Masterclass

This masterclass compiles the toughest architectural interview questions on Authentication and Authorization with senior/staff-level, high-impact answers.

### Q1: [JWT Invalidation] How do you handle JWT invalidation under high-throughput (e.g., millions of requests per minute) without turning JWTs back into stateful, database-bound sessions?
* **Answer**: You must implement a **Hybrid Revocation Cache** pattern:
  1. Enforce extremely short lifespans for Access Tokens (e.g., 5 to 15 minutes) and longer lifespans for Refresh Tokens.
  2. Embed a unique UUID claim (`jti` - JWT ID) in every access token.
  3. Upon a revocation event (e.g., user logs out, account gets suspended), calculate the token's remaining time-to-live (`exp - now`) and write the `jti` to an append-only distributed Redis cache: `SETEX blacklist:jti:<jti> <TTL> "revoked"`.
  4. The Gateway/API service verifies the token cryptographically first (fast, local CPU bound). If the signature is valid, it performs a sub-millisecond $O(1)$ read to check if the `jti` exists in the Redis blacklist.
  5. By setting the Redis key TTL equal to the token's remaining lifetime, keys self-delete once the token naturally expires, keeping memory usage bounded while preserving stateless scalability for 99% of requests.

### Q2: [Login/Logout Token Lifecycle] Upon user login and logout, what exact actions must be taken on both the client and backend to manage the token's lifecycle securely?
* **Answer**: 
  - **On Login**:
    - **Session ID Regeneration**: If utilizing stateful sessions, immediately destroy the pre-login anonymous session ID and generate a new one to prevent Session Fixation.
    - **Secure Cookies Injection**: If utilizing JWTs, the Auth Server generates a short-lived Access Token and a long-lived Refresh Token. It injects the Refresh Token into the client's browser using an `HttpOnly`, `Secure`, `SameSite=Strict` cookie.
  - **On Logout**:
    - **Client-Side Cleansing**: Clear any in-memory access tokens. Set the Cookie expiration date to a historical timestamp (e.g., `1970-01-01`) to force the browser to immediately delete the token.
    - **Backend Session Revocation**: In the database/Redis, immediately delete the active session ID or invalidate the current refresh token's family.
    - **Access Token Blacklisting**: If absolute instant revocation is required, extract the `jti` of the current access token and add it to the Redis blacklist with a TTL matching its remaining lifetime.

### Q3: [Refresh Token Rotation (RTR)] Explain the dynamic mechanics of Refresh Token Rotation and how it mitigates token theft.
* **Answer**: Under Refresh Token Rotation (RTR), refresh tokens are strictly single-use-only. 
  1. Every time a client calls `/refresh` to obtain a new Access Token, the server invalidates the submitted Refresh Token (`RT_1`) and issues a brand-new, linked Refresh Token (`RT_2`) along with the new Access Token.
  2. The server links these tokens cryptographically in a parent-child genealogy (token family) inside a fast storage layer like Redis.
  3. **Reuse Detection (The Security Trap)**: If an attacker steals `RT_1` and attempts to replay it, or if a legitimate client attempts a replay due to race conditions:
     - The server detects that the submitted `RT_1` has already been marked as `used`.
     - Assuming a security compromise has occurred, the server instantly triggers a **fail-closed action**: it revokes the entire token family (invalidating `RT_2` and any active downstream sessions descended from that login).
     - The legitimate user is logged out globally and forced to supply primary credentials, neutralizing the attacker's stolen token.

### Q4: [JWKS Deep Dive] How does dynamic JWKS fetching operate, and how do you protect the JWKS client from network failure or denial-of-service vulnerabilities?
* **Answer**: In an asymmetric signature system (e.g., RS256), downstream APIs fetch public keys from the Auth Server's JWKS endpoint to verify token signatures on-the-fly. To prevent this from becoming a single point of failure or an attack vector:
  1. **In-Memory Caching**: Downstream APIs cache JWKS keys in-memory with a long TTL (e.g., 24 hours) to verify 99% of tokens locally at $O(1)$ speed.
  2. **Stale-While-Revalidate**: If the cache is expired, continue using cached keys to verify signatures while fetching updated keys in a non-blocking background thread.
  3. **Throttled Dynamic Fetching**: If a token arrives with an unknown `kid` (e.g., during a key rotation), the verifier should dynamically pull the latest JWKS. However, this must be rate-limited (e.g., max 1 fetch per 10 seconds). Without this rate-limiter, an attacker could send random `kid` values in rapid succession, forcing your APIs to flood the Auth Server with JWKS requests, effectively orchestrating a DDoS attack.
  4. **Key Rotation Grace Period**: Keep old keys in the JWKS for at least 48 hours after introducing new keys.

### Q5: [JWT in Microservices] Where and when should JWTs be verified in a distributed microservices network? What are the architectural trade-offs?
* **Answer**: There are two primary architectural patterns:
  - **Edge-Only Verification (Gateway Translation)**:
    - *Approach*: The API Gateway handles 100% of cryptographic validation (JWKS fetch, signature check) at the perimeter. It then translates the JWT claims into plain HTTP headers (e.g., `X-User-ID: 123`) and passes them downstream.
    - *Pros*: Maximum performance. Downstream microservices don't need cryptographic libraries, complex caches, or keys. High throughput, low latency.
    - *Cons*: Weak internal security. If an attacker gains entry into the internal network (lateral movement), they can easily spoof headers.
  - **Zero-Trust Verification (End-to-End Cryptography)**:
    - *Approach*: The Gateway validates the external token and generates a highly short-lived (e.g., 60-second), symmetrically signed internal JWT (HS256) containing clean user claims. Every downstream microservice must verify this signature locally.
    - *Pros*: High security. Immune to internal lateral packet spoofing.
    - *Cons*: CPU overhead on every downstream service hop.
  - *Staff-Level Recommendation*: Implement **Edge-Only Verification** behind a strict private subnet/VPC with Network Security Policies (or Service Mesh like Istio mTLS) to block spoofing, ensuring high performance while maintaining secure network isolation.

### Q6: [Multi-Tenant JWT Design] How do you design and scale JWT-based authentication for a SaaS platform with strict tenant isolation?
* **Answer**: A secure, scalable multi-tenant JWT architecture utilizes these patterns:
  1. **Tenant-Scoped Metadata**: Embed a `tenant_id` claim in both the JWT payload (`tid`) and the token header. Include a tenant-scoped issuer URL in the `iss` claim (e.g., `https://auth.saas.com/tenants/tenant_a`).
  2. **Isolated Signing Keys**: For enterprise-grade tenants, sign JWTs with tenant-specific asymmetric keys. Downstream services fetch public keys dynamically using tenant-specific paths: `https://auth.saas.com/tenants/<tenant_id>/.well-known/jwks.json`.
  3. **Gateway Header Propagation**: The API Gateway reads the domain/subdomain or token header, routes the request, verifies the signature against the matching tenant's JWKS, and injects a sanitized `X-Tenant-ID` HTTP header downstream.
  4. **Database Gating**: Downstream microservices receive `X-Tenant-ID`, and automatically inject it into database queries, database connection pool selectors, or utilize PostgreSQL Row-Level Security (RLS) to prevent cross-tenant data leaks.

### Q7: [LocalStorage vs. Cookies] Is it better to store JWTs in LocalStorage or in HttpOnly Cookies? How do you mitigate the security trade-offs?
* **Answer**: Storing highly sensitive tokens (Refresh Tokens and long-lived Access Tokens) in **HttpOnly Cookies** is the secure production standard.
  - **The LocalStorage Dilemma**: Storing tokens in LocalStorage makes them fully accessible to JavaScript. If your site has a single Cross-Site Scripting (XSS) vulnerability (via third-party scripts, CDNs, or injection), an attacker can easily run `localStorage.getItem("token")` and steal the user's session.
  - **The HttpOnly Cookie Advantage**: `HttpOnly` cookies are inaccessible to JavaScript. XSS attacks cannot extract the token.
  - **The CSRF Trade-off**: Cookies are automatically sent by browsers on outgoing cross-site requests, making them vulnerable to Cross-Site Request Forgery (CSRF). To mitigate this:
    1. Set **`SameSite=Lax` or `SameSite=Strict`** and **`Secure`** flags on the cookie.
    2. Require a custom HTTP request header (e.g., `X-Requested-With: XMLHttpRequest` or a cryptographically verified `X-CSRF-Token` header) for any state-changing mutations (POST, PUT, DELETE). Since cross-site attackers cannot forge custom headers in cross-origin requests, this guarantees comprehensive protection against both XSS and CSRF.
