# Vector Databases & Vector Search

Comprehensive study guide covering high-dimensional embeddings, similarity metrics, Approximate Nearest Neighbor (ANN) algorithms, image/multimodal search pipelines, PostgreSQL pgvector, and distributed hybrid search architectures.

---

## 1. Why Vector Databases?

Traditional relational (SQL) and document (NoSQL) databases are optimized for scalar queries: searching by exact keys, ranges, or text prefixes. However, they fail when performing **semantic search** or **similarity-based search** (e.g., finding "articles about cloud security" when the article only uses the term "VPC and IAM security").

### Why Traditional DBs Fail at High-Dimensional Search:
1. **The Curse of Dimensionality**: In high-dimensional spaces (typically 768 to 1536 dimensions for modern embeddings), distance calculations are computationally expensive.
2. **Failure of traditional B-Tree/LSM-Tree Indexes**: B-Tree and LSM-Tree indexes rely on a single-dimensional ordering of data. In high-dimensional space, there is no natural linear order.
3. **$O(N)$ Exhaustive Search**: Without specialized spatial indexes, finding the nearest neighbors requires a full table scan ($O(N)$ complexity) to calculate the distance from the query vector to *every* record. Under scale, this latency is unacceptable ($>1000\text{ms}$).

## 2. Core Concepts: Embeddings & Similarity Metrics

### Embeddings
An **embedding** is a dense, continuous vector representation of unstructured data (text, images, audio, user behavior) generated by machine learning models (e.g., OpenAI `text-embedding-3-small`, BERT, ResNet, CLIP). 
* **Key Property**: Semantic similarity translates to geometric closeness. If two concepts are semantically related, their vectors will be close in the high-dimensional vector space.

### Similarity & Distance Metrics
To determine how similar two vectors $\mathbf{u}$ and $\mathbf{v}$ are, vector databases calculate distances. The three most common metrics are:

```
      Cosine Similarity                      Euclidean (L2) Distance
             ^                                         ^
             |  v                                      |   u
             | /                                       |  /|
             |/ _ \ theta                              | / | d(u,v)
             +-----> u                                 +-----> v
    (Focus on angle/direction)               (Focus on absolute distance)
```

#### 1. Cosine Similarity (Distance: $1 - \text{similarity}$)
Measures the cosine of the angle $\theta$ between two vectors. It focuses entirely on the **direction** of the vectors rather than their magnitude.
$$\text{Cosine Similarity} = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\| \|\mathbf{v}\|} = \frac{\sum_{i=1}^n u_i v_i}{\sqrt{\sum_{i=1}^n u_i^2} \sqrt{\sum_{i=1}^n v_i^2}}$$
* **Range**: $[-1, 1]$ (usually $[0, 1]$ for normalized text embeddings).
* **Use Case**: Best for text search, where document length (which increases vector magnitude) should not affect semantic similarity.

#### 2. Euclidean Distance (L2 Distance)
Measures the straight-line distance between two points in Euclidean space.
$$d(\mathbf{u}, \mathbf{v}) = \sqrt{\sum_{i=1}^n (u_i - v_i)^2}$$
* **Range**: $[0, \infty)$. A distance of $0$ means identical vectors.
* **Use Case**: Best for physical data, raw audio processing, or when the magnitude of the features carries critical information.

#### 3. Dot Product (Inner Product)
Measures the projection of one vector onto another.
$$\mathbf{u} \cdot \mathbf{v} = \sum_{i=1}^n u_i v_i$$
* **Range**: $(-\infty, \infty)$.
* **Special Case**: If the vectors are **unit-normalized** (magnitude $\|\mathbf{u}\| = \|\mathbf{v}\| = 1$), the Dot Product is mathematically identical to Cosine Similarity.
* **Use Case**: Best for high-throughput production systems using normalized vectors, as Dot Product is highly hardware-optimized (using SIMD/AVX instructions) and requires no expensive square-root or division calculations.

## 3. Approximate Nearest Neighbor (ANN) Indexing

To bypass $O(N)$ exhaustive search, vector databases trade absolute accuracy (recall) for extreme speed using **Approximate Nearest Neighbor (ANN)** indexing. ANN indexes organize vectors into structures that allow $O(\log N)$ or $O(1)$ search lookups.

```
       IVF (Inverted File)                      HNSW (Hierarchical Graph)
  +-------------------------+                     Layer 2:  O========O (Fast skip)
  |   * (Centroid 1)        |                               |        |
  |  / \  o  o              |                     Layer 1:  O--O--O--O (Medium)
  | o   o                   |                               |  |  |  |
  |          o  * (Centroid2)                     Layer 0:  O-O-O-O-O-O (Detailed)
  +-------------------------+
 (Partition space into clusters)               (Multi-layer graph traversal)
```

### A. HNSW (Hierarchical Navigable Small World)
HNSW is the gold standard for high-performance vector search. It organizes vectors into a multi-layered graph, heavily inspired by the probabilistic **Skip List** data structure.
* **Structure**:
  - **Upper Layers**: Contain sparse graphs with long-distance links. Traversal starts here to quickly jump across the vector space (global routing).
  - **Lower Layers**: Contain denser graphs with shorter links. As the search approaches the target, it drops to lower layers to refine the search (local routing).
  - **Layer 0**: Contains all vectors, fully connected with nearest-neighbor links.
* **Pros**: Extremely fast query latency ($O(\log N)$); highest recall accuracy.
* **Cons**: Massive memory footprint (entire graph structure must be cached in RAM); slow index build/insert times.

### B. IVF (Inverted File Index)
IVF divides the vector space into a fixed number of Voronoi cells using **K-Means Clustering**.
* **Structure**:
  1. During index building, the database identifies $K$ central points (centroids).
  2. Every vector is assigned to its nearest centroid, creating an "inverted list" (posting list) per cluster.
  3. **Query Path**: The database calculates the distance from the query vector to the $K$ centroids. It then scans *only* the vectors in the $N$ closest centroids (defined by the `nprobe` parameter), completely skipping the rest of the database.
* **Pros**: Low memory footprint; quick index building.
* **Cons**: Lower recall if a vector lies near cluster boundaries; query speed degrades if `nprobe` is set too high to reclaim accuracy.

### C. Quantization: Fitting Vectors into RAM
A database with 100 million vectors of 1536 dimensions (Float32) requires:
$$100,000,000 \times 1536 \times 4 \text{ bytes} \approx 614 \text{ GB of raw RAM}$$
To make this cost-effective, vector DBs use compression techniques:

1. **Scalar Quantization (SQ)**:
   - Converts 32-bit floating-point numbers (`Float32`) to 8-bit integers (`INT8`).
   - Reduces memory usage by **$75\%$** with a minor loss in recall ($1-2\%$).
2. **Product Quantization (PQ)**:
   - Divides a high-dimensional vector into $M$ smaller sub-vectors.
   - Clusters each sub-space independently and assigns a short byte-code (representing cluster centroids) to each sub-vector.
   - Reduces memory footprint by up to **$95\%$** but introduces higher calculation overhead and some loss in recall.

## 4. Multi-Modal & Image Search System Architecture

Modern search engines leverage multi-modal models like **CLIP (Contrastive Language-Image Pre-training)** to enable both **Image-to-Image** and **Text-to-Image (Natural Language)** search. CLIP is trained on pairs of text and images to map both modalities into a **shared, unified vector space**.

```
[Text Query] ──> [Text Encoder] ────┐
                                    v
                             (Shared Space) <── [Vector Search] ──> [Image Results]
                                    ^
[Raw Images] ──> [Image Encoder] ───┘
```

### End-to-End Image Search Pipeline:

```
1. Write/Ingestion Path:
   [Raw Image File] ──> [Feature Extraction (ResNet/CLIP)] ──> [Vector Embedding (e.g. 512-dim)]
                                                                      |
   [Image ID / S3 Metadata] <── [Database ID Sync] <────────── [Insert into Vector DB]

2. Read/Query Path:
   [User Uploads Image] ──> [Feature Extraction] ──> [Search Vector DB] ──> [Fetch Metadata] ──> [S3 CDN Image URLs]
```

#### A. Ingestion (Index Building):
1. **Upload**: Administrator uploads product images to the system.
2. **Storage**: Images are saved in an Object Store (Amazon S3 / MinIO), returning an immutable file path/URL.
3. **Inference (Embedding Generation)**: The image file is sent to an inference service running an Image Encoder (e.g., CLIP ViT, ResNet50).
4. **Vector Persistence**: The resulting 512-dimensional vector is saved in the Vector Database (e.g., Qdrant) along with its metadata:
   ```json
   {
     "id": "prod_99122",
     "vector": [0.0124, -0.0984, ..., 0.5412],
     "payload": {
       "image_url": "https://cdn.saas.com/images/prod_99122.webp",
       "category": "footwear",
       "tags": ["running", "sports"]
     }
   }
   ```

#### B. Query (Image-to-Image Search):
1. User uploads a photo of a shoe to the mobile client.
2. The backend proxies the image to the Image Encoder model, producing a query vector $\mathbf{q}$.
3. The backend executes a $K$-Nearest Neighbors query against the Vector DB using the Cosine Distance operator:
   ```sql
   SELECT id, payload.image_url, cosine_distance(vector, q) AS dist
   FROM products
   ORDER BY dist ASC
   LIMIT 10;
   ```
4. The database uses HNSW to return the top 10 most similar product records in milliseconds.

## 5. PostgreSQL pgvector: Deep Dive

For projects that want to avoid the operational overhead of spinning up a dedicated cluster (like Milvus or Qdrant), PostgreSQL's first-party extension **pgvector** is an incredibly powerful, ACID-compliant solution.

### Core pgvector Operations:

```sql
-- 1. Enable the extension
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. Create table with a vector column (e.g., OpenAI text-embedding-3-small length)
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    content TEXT NOT NULL,
    embedding vector(1536) -- Explicit dimension constraint
);

-- 3. Perform a similarity query
-- Operator <=> is Cosine Distance (1 - Cosine Similarity)
-- Operator <-> is L2 (Euclidean) Distance
-- Operator <#> is Negative Inner Product (Dot Product)
SELECT id, title, title <=> '[0.012, -0.051, ..., 0.124]'::vector AS distance
FROM articles
ORDER BY distance
LIMIT 5;
```

### pgvector Indexing Strategies

Without an index, pgvector falls back to an exact $O(N)$ sequential scan (Flat search). For production scaling, you must build an index:

#### 1. IVFFlat Index (Inverted File Flat)
```sql
CREATE INDEX articles_ivfflat_idx ON articles 
USING ivfflat (embedding vector_cosine_ops) 
WITH (lists = 100);
```
* **Lists Parameter**: Represents the number of centroids. Recommended value: $\text{Table Rows} / 1000$ for tables under 1M rows, and $\sqrt{\text{Table Rows}}$ for larger datasets.
* **Important Constraint**: You **must** populate the table with representative data *before* creating an IVFFlat index, as the K-means clustering needs a baseline distribution to place centroids accurately. If your data grows significantly, you must rebuild the index (`REINDEX`).

#### 2. HNSW Index (Hierarchical Navigable Small World - Added in v0.5.0)
```sql
CREATE INDEX articles_hnsw_idx ON articles 
USING hnsw (embedding vector_cosine_ops) 
WITH (m = 16, ef_construction = 64);
```
* **m**: Max number of connections per node in the graph (default: 16). Higher = better recall, higher build time and RAM.
* **ef_construction**: Size of dynamic candidate list during index building (default: 64).
* **Advantage**: Unlike IVFFlat, pgvector's HNSW can be built on an empty table and updates dynamically as rows are added, with superior recall/latency profiles.

## 6. Hard Interview Questions & Deep Answers

### Q1: What is Hybrid Search, and how do you implement Reciprocal Rank Fusion (RRF) to merge keyword (BM25) and semantic vector scores?
**Answer**:
* **Hybrid Search** combines traditional sparse keyword search (Elasticsearch BM25 or Postgres tsvector) and dense semantic vector search. Sparse search excels at finding exact product codes, serial numbers, or unique names (e.g., "iPhone 15 Pro Max"). Dense search excels at conceptual intent (e.g., "durable water-resistant outdoor gears").
* **The Problem**: BM25 scores are unbounded (ranges like $0$ to $30+$ depending on text length), while Cosine distance is bounded between $0$ and $2$. You cannot directly add or multiply these scores.
* **The Solution: Reciprocal Rank Fusion (RRF)**:
  RRF is a highly robust, model-agnostic algorithm that ignores the raw score values. Instead, it evaluates the *rank* (position) of each item in both search results.
  $$\text{RRF Score}(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
  Where $M$ is the set of search algorithms (Keyword and Vector), $r_m(d)$ is the rank of document $d$ in system $m$, and $k$ is a constant (typically $60$) that dampens the influence of high-ranking outliers.

```go
// Go implementation snippet for RRF
type SearchResult struct {
	DocID string
	Rank  int
}

func ReciprocalRankFusion(keywordResults, vectorResults []SearchResult) map[string]float64 {
	const k = 60.0
	scores := make(map[string]float64)

	// Process keyword ranks
	for _, res := range keywordResults {
		scores[res.DocID] += 1.0 / (k + float64(res.Rank))
	}

	// Process vector ranks
	for _, res := range vectorResults {
		scores[res.DocID] += 1.0 / (k + float64(res.Rank))
	}

	return scores // Sort map descending to get the ultimate merged ranking
}
```

### Q2: How do you handle metadata filtering (e.g., "search shoes similar to vector X, but only if they are under $50 and in stock") in a high-scale vector database?
**Answer**:
Standard vector indexes (like HNSW) are blind to relational metadata. There are three approaches to metadata filtering:

1. **Pre-Filtering (Filter, then Search)**:
   - Filter the relational database first (e.g., fetch all shoe IDs under $50).
   - Perform an exhaustive vector search over *only* those IDs.
   - *Failure Point*: If the filter matches millions of items, the vector DB must fall back to a slow, brute-force search over the filtered subset.
2. **Post-Filtering (Search, then Filter)**:
   - Perform a standard HNSW vector search to fetch the top 1000 nearest neighbors.
   - Discard all results that are over $50 or out of stock.
   - *Failure Point (The Single-Category Problem)*: If "shoes under $50" are rare in the dataset, your top 1000 closest vectors might contain *zero* items that fit the filter, resulting in empty search results for the user.
3. **Single-Stage Filtering (Hybrid/In-Index Filtering - Best Practice)**:
   - Used by modern databases (Qdrant, Milvus, Pinecone, pgvector).
   - The HNSW graph traversal is itself aware of the metadata index. During graph traversal (moving from node to node), the search algorithm checks metadata constraints and immediately prunes nodes that do not match the metadata filters. This guarantees both $O(\log N)$ query speed and perfect accuracy.

### Q3: How do you handle real-time vector updates and index rebuilds in HNSW/IVF without causing query downtime or high CPU starvation?
**Answer**:
Vector index builds are extremely CPU and memory intensive. Rebuilding an HNSW graph or re-clustering IVF centroids in-place can freeze query pipelines.
- **Dedicated Ingestion vs. Query Segregation**: In a distributed setup (e.g., Milvus/Qdrant clusters), write/indexing paths are separated from read/search paths. Write-nodes continuously consume from a message log (e.g., Kafka) and build segments in the background, while Read-nodes serve queries from read-only, immutable memory-mapped index segments.
- **Double-Buffering (Shadow Indexes)**: On single-node systems (like PostgreSQL), you build a shadow index in the background using concurrent operators:
  ```sql
  -- Build index concurrently without blocking parallel SELECTs on the table
  CREATE INDEX CONCURRENTLY articles_hnsw_new_idx ON articles USING hnsw (...);
  
  -- Once built, drop the old index inside a quick metadata transaction
  BEGIN;
    DROP INDEX articles_hnsw_old_idx;
  COMMIT;
  ```
- **Dynamic Segment Merging (similar to LSM-Trees)**: Maintain a small, unindexed, highly-write-optimized memory buffer (Active Segment) for real-time inserts. Queries scan both the main HNSW index and perform a brute-force check on the tiny active buffer. Once the active buffer reaches a threshold (e.g., 50,000 vectors), a background worker builds a new immutable HNSW segment and merges it into the main index pool using a background compaction loop.
