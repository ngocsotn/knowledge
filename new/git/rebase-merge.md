# Git Merge vs. Git Rebase

Comprehensive interview study guide covering branch integration strategies, history rewriting, squash merges, conflict resolution, and the golden rule of rebasing.

---

## 1. Merge vs. Rebase: The Integration Strategies

When merging changes from a feature branch back into the main branch, Git offers two primary strategies with completely different historical outcomes:

```
              Merge (Creates Merge Commit)                 Rebase (Linear History)
               A ─── B ─── C (main)                        A ─── B ─── C (main)
                \           \                                           \
                 D ─── E ────► M (HEAD)                                  D'─── E' (HEAD)
```

### 1. Git Merge
* **Mechanism:** Integrates the branches by creating a brand new, dedicated **Merge Commit** (M) that has two parent commits.
* **Pros:** Non-destructive. It preserves the complete, authentic chronological history and context of when branches were created and merged.
* **Cons:** Log histories can become cluttered with redundant "Merge pull request..." commits, resulting in a complex "spaghetti" history graph.

### 2. Git Rebase
* **Mechanism:** Rewrites the commit history. It finds the common ancestor of the two branches, temporarily lifts the unique commits of your feature branch, applies the new commits from `main` first, and then replays your feature commits on top of the new HEAD.
* **Pros:** Creates a clean, perfectly **linear log history** with zero merge commits, making history inspection and debugging (like `git bisect`) trivial.
* **Cons:** Destructive—it rewrites history by generating brand-new commit hashes (`D'` and `E'`) for your changes.

---

## 2. Squash Merging & Interactive Rebasing

* **Squash Merging:** Combines all individual commits from a feature branch (e.g., 20 WIP commits like "fix typo", "test again") into a **single, unified commit** upon merging. This keeps the main branch clean and concise.
* **Interactive Rebasing (`git rebase -i HEAD~N`):** A powerful tool used to clean up local history before publishing. It opens an editor allowing you to:
  * **pick:** Keep the commit.
  * **reword:** Edit the commit message.
  * **squash:** Combine the commit with the previous one.
  * **drop:** Delete the commit entirely.

---

## 3. The Golden Rule of Rebasing

> **"Never rebase commits that have been pushed to a public repository."**

* **Why:** If you rebase a shared public branch (like `main` or `develop`), you rewrite commit hashes that other developers have already pulled and branched off of. When they pull the rebased branch, Git will see duplicate commits with different hashes, forcing them into complex, manual merge loops, corrupting the repository state.

## 4. Popular Interview Questions & High-Impact Answers

### Q1: What is the "Golden Rule of Rebasing" and what happens if you violate it?
* **Answer:** The Golden Rule is to **never rebase commits that have been pushed to a public, shared repository**. Rebasing rewrites history by generating completely new commit hashes for existing changes. If you violate this rule and force-push (`git push --force`) a rebased shared branch, you invalidate the commit history for everyone else on the team. When they attempt to pull, Git will try to merge their local history with the rewritten history, creating duplicate commits and severe merge conflicts, disrupting the team's workflow.

### Q2: What is a Squash Merge, and what are its pros and cons?
* **Answer:** A **Squash Merge** takes all commits from a pull request feature branch and condenses them into a single, clean commit on the destination branch.
  * **Pros:** Keeps the destination branch's git log completely clean and readable, grouping feature implementations into single, atomic commits. It also allows developers to commit frequently ("work-in-progress" commits) during local development without polluting the public history.
  * **Cons:** It destroys the granular history of the feature branch, losing the context of intermediate code changes, design revisions, or specific dates.

### Q3: How does the `git bisect` command help locate bugs, and why does it benefit from a linear Git history?
* **Answer:** **`git bisect`** is a debugging tool that uses **binary search** to find the exact commit that introduced a bug:
  1. You mark your current commit as "bad" and a known older commit in the past as "good."
  2. Git splits the history in half, checkouts the middle commit, and asks you to test.
  3. You mark it as "good" or "bad." Git repeats this, locating the buggy commit in $O(\log N)$ steps.
  * **Linear History Benefit:** If your history is messy with complex parallel merge branches (spaghetti graphs), `git bisect` can land on invalid intermediate states or dead merge paths, making debugging difficult. A clean, linear history generated by rebasing guarantees reliable binary searching.
